CMFGEN End-to-End Processing Pipeline and File I/O Map
Date: 2026-02-08
Repository snapshot: /home/karpov/CMFGEN2023/cur_cmf

Purpose
-------
This document is a consolidated, step-by-step map of file processing across:
1) helper scripts used to stage/transfer model directories,
2) CMFGEN main runs,
3) CMF_FLUX post-processing runs,
4) helper-script post-processing around CMF_FLUX outputs.

Source investigations consolidated here:
- txt_files/CMFGEN_input_file_investigation_2026-02-08.txt
- txt_files/CMFGEN_output_file_investigation_2026-02-08.txt
- txt_files/CMFGEN_cmf_flux_file_io_investigation_2026-02-08.txt

Conventions
-----------
- READ: file consumed by a component.
- WRITE: new/overwritten output file.
- UPDATE: in-place keyword update, rename, symlink swap, or copy into canonical alias name.
- File names are runtime working-directory names unless a directory prefix is explicitly shown.


Step 1. Pre-run directory staging (helper scripts)
===================================================
Component: `com/cpmod.sh`, `com/drad_cpmod.sh`, `com/sn_update.sh`, `com/out2in.sh`, `com/mv_n.sh`, `com/mvscr.sh`

READ
- Existing model control/data from source run directory, e.g. `batch.sh`, `IN_ITS`, `VADAT`, `*OUT`, `GAMMAS`, `MODEL_SPEC` (`com/cpmod.sh:45-50`, `com/drad_cpmod.sh:49-54`).
- Optional SN continuation files: `JH_AT_CURRENT_TIME`, `JH_AT_CURRENT_TIME_INFO`, `SN_HYDRO_FOR_NEXT_MODEL`, `CUR_MODEL_DATA` (`com/drad_cpmod.sh:63-67`, `com/sn_update.sh:46-68`).

WRITE
- Staged inputs in target directory:
  - `GAMMAS_IN` from `GAMMAS` (`com/cpmod.sh:49`, `com/drad_cpmod.sh:53`).
  - `SN_HYDRO_DATA` from `SN_HYDRO_FOR_NEXT_MODEL` (`com/drad_cpmod.sh:66`, `com/sn_update.sh:68`).
  - `OLD_MODEL_DATA` from `CUR_MODEL_DATA` (`com/drad_cpmod.sh:67`, `com/sn_update.sh:61`).
  - `JH_AT_OLD_TIME` and `_INFO` from current-time files (`com/drad_cpmod.sh:63-64`, `com/sn_update.sh:47-55`).

UPDATE
- Family rename `*OUT -> *_IN` (invoked via `out2in`) (`com/out2in.sh:5-9`, `com/cpmod.sh:160`).
- Explicit ion renames (subset) such as `Mg2OUT -> Mg2_IN` (`com/mv_n.sh:1-15`).
- When copying within same directory: `GREY_SCL_FAC_IN -> GREY_SCL_FAC_SAVE` (`com/cpmod.sh:22`, `com/drad_cpmod.sh:27`).
- Restart pointer promotion: `NEW_POINT1 -> POINT1`, `NEW_POINT2 -> POINT2`, `NEW_SCRTEMP -> SCRTEMP` (`com/mvscr.sh:1-3`).

Step 11. LTE utility pipeline (`main_lte.exe` / `wind_hyd.exe`)
================================================================
Component: `lte_hydro/lte.f` + `lte_hydro/lte_sub.f` (`main_lte.exe`), and `lte_hydro/wind_hyd.f` (`wind_hyd.exe`)

Key path finding (for your `lte/` subfolder question)
- No code path in this snapshot creates a directory literally named `lte/`:
  - no `mkdir lte`, no `cd lte`, and no hard-coded `FILE='lte/...'`.
- Both LTE executables open/write bare filenames in the current working directory.
- Therefore, files appearing under a run directory’s `lte/` subfolder are produced when the executable is launched from that subfolder by external workflow convention (not by internal directory-creation logic).

11A) Typical launch path
- `lte_hydro/Makefile` builds:

- `OBSFLUX` -> `obs_cmf*`
- `MEANOPAC` -> `meanopac*`

Important negative finding:
- `hydro_cont` is not defined by built-in writers or helper rename paths in this snapshot.


Operational notes for future viewer/launcher
=============================================
1) Always track both native and alias filenames in scan logic.
2) Preserve mutable controls (`VADAT`, `IN_ITS`, `HYDRO_DEFAULTS`, `ADJUST_R_DEFAULTS`, `CMF_FLUX_PARAM`) as versioned snapshots.
3) For direct-access binaries, require `_INFO` sidecars before attempting parse.
4) Treat script-level aliases as workflow conventions, not guaranteed outputs.
